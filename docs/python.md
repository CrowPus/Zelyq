# Python backend implementation plan

Status: phases 1–3 implemented and verified; phases 4–6 partly implemented, see
[Implementation state](#implementation-state).  
Date: 2026-09-18.  
Scope: Python backends for applications generated by Zelyq.

This plan follows a source review of project creation, templates, agent prompts,
runtime drivers, previews, verification, Supabase integration, snapshots, CI, and
deployment configuration. The repository findings below describe existing code.
The contract, runtime, template, and deployment work described here now exists;
the database-integration and evaluation work described in phases 4–6 does not
yet, and is listed explicitly below. No performance claim has been measured.

## 1. Product objective

Let someone describe an application that needs Python, have Zelyq build its React
interface and Python API, and use both through one working preview. The resulting
project must run outside Zelyq with documented commands and a tested deployment
artifact.

Python remains backend-only. The first supported combination is **React + Vite +
TypeScript with FastAPI**, presented as **React + Python backend** in project
creation. Existing React and Expo projects retain their current behavior.

**A project can save data before anyone configures anything.** Every project of
this stack owns a SQLite database from the moment it is created — writable, with
the application owning its schema, stored outside the source tree. Requiring a
database to be procured before an app can remember anything is not how a build
tool works: the first app most people ask for is a list of things, and it has to
run. This corrects the original framing of this plan, which made persistence a
configuration step and left a new project unable to save a row.

**Connecting your own database is an upgrade, not the price of entry.** A user's
PostgreSQL or MySQL, an existing schema, or Supabase are chosen deliberately in
Backend settings, and the models and routes written against the local database
carry over. From that point the protections in this document apply in full, and
they are strict because the data is not the application's to lose. Database
choice and application authentication remain separate decisions.

The first release keeps Zelyq's server, agent, shared protocol, database layer,
and runtime host in TypeScript. [ADR 0002](adr/0002-node-typescript-monorepo.md)
records why the platform previously moved away from mixed Python/TypeScript
tiers. A generated application's Python service belongs behind the existing
runtime boundary and an explicit HTTP contract.

### User value

| Application | Why offer a Python backend? | Initial scope |
| --- | --- | --- |
| Spreadsheet import and reporting | Validate and transform CSV/Excel data with Python libraries, then display results in React. | Bounded CSV import is the first reference workflow; Excel is a later example. |
| Existing Python business tool | Give an existing calculation or processing module an API and usable interface. | Support code incorporated into the supported project layout. |
| Custom business application | Keep validation, integration credentials, and business operations on the server. | Supported through FastAPI routes and explicit access checks. |
| Application over an existing database | Build an interface and business API around data the user already owns. | Connect to supported user-managed databases and map existing schemas without requiring migration to Supabase. |
| Prediction or classification application | Expose Python model inference through an API. | Later, after resource limits and model dependency requirements are established. |
| Long-running processing | Run imports, reports, or document processing with durable progress and retries. | Later worker capability; not an implicit part of the first template. |

These are candidate use cases, not measured user demand. Python should not be
automatically added to a static website or an application adequately served by
the existing Supabase integration. The agent should explain the concrete reason
for a Python service and its additional hosting and maintenance requirements.

### First-release boundaries

Include one FastAPI starter, managed frontend/API previews, backend verification,
project-scoped configuration, user-managed PostgreSQL and MySQL connections,
SQLite for local/single-instance applications, optional Supabase integration,
and an independently runnable production container. Both existing schemas and
new application-owned schemas are in scope. Exact engine/driver versions must
be selected and tested in phase 1.

Defer Django/Flask starters, Python-rendered interfaces, Expo/Python integration,
arbitrary standalone Python repository import, GPU execution, model training,
durable job queues, scheduled workers, and automatic conversion of existing
projects. Additional engines such as MongoDB and SQL Server require their own
adapter and validation scope; do not claim every database is supported because
a Python driver exists. A Python API without persistence must also work without
any database connection.

## 3. Target architecture

```text
Zelyq editor / agent
        |
        v
Existing TypeScript server and RuntimeDriver
        |
        +-- managed React/Vite service -- one public preview address
        |             |
        |             +-- /api/* proxy --> managed FastAPI service
        |                                      |
        |                                      +-- selected user database
        |                                      +-- selected authentication provider
        |                                      +-- optional Supabase services
        |                                      +-- configured external APIs
        |
        +-- installation, logs, health, checks, stop/restart, source snapshots
```

The generated API never accesses Zelyq's own database, provider credentials,
session bridge tokens, or internal administrative routes. Application users and
Zelyq editor users are different identity domains.

### Framework and tooling

- FastAPI with Pydantic request/response models and Uvicorn serving the API.
- `uv`, `pyproject.toml`, `uv.lock`, and a project-local virtual environment.
- SQLAlchemy for the supported direct SQL connections, with a tested driver per
  engine; Alembic for new application-owned schemas. Existing externally managed
  schemas retain their owner's migration process.
- Ruff for lint/format checks, mypy for Python type checking, and pytest with
  HTTPX for API behavior tests.
- Existing React/Vite/TypeScript tooling for the frontend.
- A generated TypeScript client from the backend's OpenAPI schema; select and
  pin the generator during the initial compatibility check.

Choose one supported CPython minor and pin concrete tool/package versions after
checking clean installation on the supported environments. Do not advertise a
broad Python compatibility range until it has been tested. CI must reject a
stale lockfile with `uv sync --locked`; ordinary startup must not silently
rewrite it. Dependency changes deliberately regenerate and review the lockfile.

FastAPI is the first framework because its typed API models and OpenAPI support
fit the existing TypeScript interface. Django offers an integrated ORM/admin
approach that may suit future application types, but adds a different set of
generation and migration conventions to support.

### Proposed generated project layout

```text
project/
  src/                         # existing React source convention
    lib/api/                   # generated API client and a small integration wrapper
  public/
  package.json
  package-lock.json
  vite.config.ts
  tsconfig.json
  zelyq.runtime.json           # proposed, versioned runtime/check definitions
  backend/
    app/
      main.py
      api/
      schemas/
      services/
      db/                     # only when direct SQL persistence is selected
    migrations/               # only for an application-owned SQL schema
    alembic.ini               # only when Alembic owns migrations
    tests/
    pyproject.toml
    uv.lock
    .python-version
    .env.example              # names/placeholders only
  scripts/                     # portable build and validation entry points
  Dockerfile
  .dockerignore
  .gitignore
  README.md
```

Keep the frontend at the project root initially to minimize changes to existing
file, designer, and inspection conventions. Runtime ownership of the API must
not depend on an agent inventing a background shell command inside `npm run dev`.

## 4. Runtime contract and lifecycle

Introduce a schema-validated, versioned `zelyq.runtime.json`. This is a proposed
file, not an existing supported format. Define the final schema in `@zelyq/core`
before building the template.

| Contract field | Required meaning |
| --- | --- |
| Schema version | Reject unsupported versions with an actionable error. |
| Required capabilities | Python/toolchain availability and managed-service protocol support. |
| Services | Stable service ID, relative working directory, executable/arguments, runtime-assigned port, readiness probe, dependency order, and required/optional status. |
| Installation | Bounded install steps and the manifests/lockfiles whose changes invalidate an installation. |
| Environment | Public configuration and backend secret references, never literal secrets. |
| Persistence | Selected adapter, approved connection reference, schema ownership, and development/test target. No embedded connection credentials. |
| Preview entry | One browser-facing service; backend services remain internal. |
| Checks | Named lint, type, test, build, and API-contract commands with timeouts. |
| Runtime data | A declared persistent data location separate from source and snapshots. |

Treat commands and project files as untrusted executable input. Validate paths
and ports, bound resources and command output, and execute through the selected
runtime. A manifest is configuration, not a security boundary. Do not accept
arbitrary secret-store identifiers or host paths from project configuration.

### Lifecycle requirements

1. Probe capabilities before installation and report missing Python/tooling
   clearly. Remote hosts must advertise support; an older host must refuse a
   Python project cleanly without claiming its preview works.
2. Serialize start/stop/restart operations per project across server and agent
   processes. Concurrent start requests must adopt the same service group.
3. Synchronize dependencies from lockfiles in each declared working directory.
   A directory's existence alone does not prove dependencies are current.
4. Allocate ports without collisions. Local backends use internal loopback ports;
   container backends use unpublished ports inside the project container.
5. Start the API, wait for a successful readiness response, then start the
   frontend with its API proxy target supplied by the runtime.
6. Persist enough process ownership and configuration revision information to
   adopt services safely after a Zelyq process restart. Do not trust a PID alone
   or serialize secret values into the process record.
7. Report readiness per service. A working Vite server with a failed API is not a
   healthy Python project. Separate liveness from readiness where dependencies
   such as a database affect whether requests can succeed.
8. On stop, deletion, startup failure, or shutdown, terminate all owned process
   groups, including reload children, and release their ports. Bound retries;
   do not restart a permanently failing API forever.

Preserve the existing aggregate preview URL and fields for old clients. Add
service details for new clients and map any failed required service to an
aggregate failure. Label logs by service and bound/redact them. Configuration or
secret rotation must restart affected services using a revision marker rather
than a secret-derived value exposed in status.

The local runtime remains a trusted-machine mode. Python virtual environments
isolate dependencies, not operating-system privileges. Shared hosting requires
the existing project isolation boundary and resource/network policy to apply to
both services. Processes within one project container belong to one project
trust boundary; separate environment maps do not make them hostile-code isolation.

## 5. API routing and frontend contract

Use a same-origin `/api` prefix on the generated application's preview address.
This belongs to the generated app, not the Zelyq editor's API. Vite proxies it to
the runtime-selected Python service. Never hardcode a laptop address or shared
fixed backend port into generated frontend code.

Provide `/api/health/live` and `/api/health/ready` without sensitive configuration
in their responses. Return validated responses and a consistent error shape;
handle validation failures, authorization failures, timeouts, and unavailable
dependencies distinctly. Bound upload sizes and processing time for the initial
CSV workflow. Support cancellation and clear UI error states where applicable.

Export OpenAPI deterministically without requiring a live database or real
secrets. Generate the TypeScript client from that artifact and verify in CI that
regeneration produces no unexpected diff. Contract checks supplement behavior
tests; matching schemas do not establish correct authorization or business logic.

Production uses a tested single-container baseline: build React in a Node build
stage, install locked Python runtime dependencies in the final Python stage,
and serve the frontend build alongside FastAPI. Reserve API routes before the
SPA fallback so an unknown API endpoint returns an API error, not `index.html`.
Run without development reload or Vite. TLS can terminate at the deployment
platform's reverse proxy. A separate frontend/API deployment is a later option.

## 6. Authentication, persistence, and configuration

### Database selection and support contract

Ask what data source the application should use, whether it already contains
data, and whether Zelyq may manage its schema. Respect an existing choice; do not
replace it with Supabase or provision a second database silently. Hosting vendor
and database engine are separate: a supported PostgreSQL connection can point to
a self-hosted or managed service, subject to verified connectivity and features.

| Persistence option | First-release behavior | Schema authority |
| --- | --- | --- |
| **Project-owned SQLite (default)** | Present from project creation, writable, no configuration. Migrations for this database only are applied before the API starts. The file lives in runtime data, outside source, snapshots and Git. | The application, through reviewed Alembic revisions. |
| No database | Available by selecting it: a stateless API with no database or credentials. | None. |
| User-managed PostgreSQL | Connect through a pinned SQLAlchemy driver, with verified TLS for remote connections and bounded pooling. Support new and existing schemas. | Existing owner, or Alembic for a new application-owned schema. |
| User-managed MySQL | Same connection/ownership workflow, with MySQL-specific integration tests and migrations. | Existing owner, or Alembic for a new application-owned schema. |
| SQLite | Explicit local/single-instance option with a persistent file in runtime data, outside source snapshots. | Existing owner, or Alembic for a new application-owned schema. |
| Supabase | Optional Auth/Data/Storage integration, or a direct PostgreSQL connection with the direct-SQL authorization rules. | Existing Supabase SQL migrations for the linked integration; otherwise the selected single schema owner. |
| Another engine | Explain the missing adapter and driver/test requirements. Preserve the user's requested target in the design. | Determined as part of that adapter's support work. |

This is a proposed support matrix, not a statement that these paths already
exist. Install only the selected driver's dependencies. SQLAlchemy dialect
support does not guarantee that engine-specific SQL, indexes, types, or migration
behavior are interchangeable. An engine change is a reviewed migration project,
not a connection-string switch.

### Connecting an existing database

Provide a project database setup flow: choose the engine, select a new or existing
schema, supply connection configuration through the secret form, choose the
environment, test connectivity, and select the permitted schema/tables. Show
masked host/database details and actionable errors without exposing credentials.

Connection checks run from the selected project runtime, where the generated API
will execute. A server-side probe alone cannot establish container/remote-host
reachability. Bound DNS/connect/query timeouts and follow the runtime's network
policy. Permit private database endpoints only through operator-authorized
network access; do not silently expose a private database or grant arbitrary
access to the Zelyq host network. TLS CA/client-certificate configuration belongs
in protected runtime configuration, not authored source.

Distinguish connectivity, read permission, write permission, and schema-management
permission. A successful `SELECT 1` proves neither application authorization nor
permission to change data. Start existing-database discovery with read-only
credentials and metadata inspection limited to the selected schema/tables.
Reflection is an aid to mapping, not evidence that every view, trigger, procedure,
or permission has been understood. Surface unsupported objects explicitly.

Give the agent only the approved schema description. Do not sample real rows or
send production data to the model by default. Use synthetic fixtures or an
explicitly authorized development copy. Existing read-only databases must remain
usable for reporting applications without granting DDL or write access.

### Schema ownership and migrations

Record one migration authority per owned schema and an explicit ownership mode:

- **Existing, externally managed schema:** map models/queries to its actual
  structure. Do not run `create_all`, initialize Alembic history, rename tables,
  or generate/apply schema changes automatically. Proposed changes remain a
  reviewable artifact for the schema owner unless management is authorized.
- **New, application-owned schema:** create reviewed Alembic migrations, exercise
  them against a disposable database of the selected engine, and apply them only
  to the designated environment with the required authorization.
- **Existing schema with authorized application management:** compare the real
  schema to the intended baseline before adopting migration history. Baselining
  must not recreate or erase existing objects or data.

Generated migration diffs require review; autogeneration is not a proof of safety.
Migrations are applied automatically for exactly one target: the project's own
SQLite build database, created by Zelyq, holding only this application's data,
selected server-side and signalled to the runtime as `ZELYQ_DB_AUTOMIGRATE`. A
custom `databaseUrl` disqualifies a database from this even when the engine is
SQLite. For every other target — a user's PostgreSQL or MySQL, an existing
schema, anything in test or production — do not apply migrations during API
startup, preview restart, or source undo. Keep runtime DML credentials separate from privileged migration
credentials. Production changes need a concrete reviewed migration and recovery
plan; connecting a database is not permission to mutate its schema.

### Direct SQL application behavior

Keep persistence access behind a small application data-access layer so API
routes do not depend on Supabase-specific clients. Use parameterized queries,
request-scoped sessions, explicit transactions for multi-step writes, and
bounded pools sized for the API worker count and the database's connection limit.
Handle disconnects and transaction rollback explicitly. Retrying a connection
does not justify replaying a write whose commit outcome is unknown.

Database credentials authenticate the service, not the application user. Enforce
user/tenant authorization in the API and its data queries; do not assume ordinary
SQL connections provide Supabase-style RLS. Use database policies as additional
protection where deliberately configured. Test denied access and transaction
failure against each supported engine, not only an in-memory SQLite substitute.

SQLite needs a persistent volume and a documented single-instance deployment
model. Do not deploy independent replicas with separate local files and imply
they share data. Never silently fall back to SQLite when a user's configured
database is unavailable.

### Authentication independent of the database

The user can use their existing identity provider with their selected database.
For the first release, define and test a standards-based OIDC/OAuth access-token
integration for a configured issuer and audience, alongside the existing
Supabase Auth integration. Pin the validation library during phase 1 and verify
signature algorithms, issuer, audience, expiry, and signing-key rotation. Reject
unsupported token formats clearly; do not treat every JWT or an ID token as a
valid API access token.

Map the verified subject to application accounts/tenant membership as required
by the user's schema. Provider login alone does not grant access to every row.
Public applications may explicitly choose no login; private applications with
missing auth configuration must not become public. Building a new password,
recovery, and session system from scratch is outside the initial starter.

### Optional Supabase integration

When the user selects Supabase, reuse its existing linked development-resource
workflow. Database access through its Data API and direct PostgreSQL access are
different modes; make the chosen mode explicit.

The following rules describe the existing Supabase Auth plus Data API path.
Selecting Supabase-hosted PostgreSQL alone does not mandate Supabase Auth; direct
SQL access follows the independent authentication and data-access rules above.

- When Supabase Auth is selected, the React client signs in through it and sends
  its access token to protected Python API operations.
- The API verifies the token using the configured project's supported verification
  mechanism, including issuer/audience/expiry checks as applicable. Never merely
  decode a token or trust a client-supplied user ID.
- Use a request-scoped data client carrying the verified user's identity for
  user-scoped Supabase operations. Avoid mutable shared authentication state.
- Preserve RLS through the Data API. A direct privileged SQL connection does not
  automatically preserve the end user's RLS context.
- Existing Supabase SQL migrations remain the schema authority for this mode.
  Do not introduce a second migration system for the same schema.
- Privileged operations require explicit authorization and narrowly scoped
  credentials; do not use administrative access for all API requests.

The existing Supabase verification tools remain useful but cannot prove the
Python routes are secure. Test two users against the actual API, including
attempts to read and modify each other's records. Signed-out and expired-token
requests must fail correctly.

The absence of a Supabase connection must never block a project configured with
its own supported database and authentication provider.

### Project configuration and secrets

Add a project configuration surface with variable names, scope, masked presence,
and replace/delete controls. Reuse existing access-control and encryption
primitives where appropriate; do not treat instance provider settings as a
generated application's secret store.

Database connections are project- and environment-scoped resources with engine,
permitted schema, ownership mode, TLS options, and secret references. Keep the
generated app's `DATABASE_URL` distinct from the Zelyq platform's own variable of
the same name through explicit service environment assembly. Never pass the
platform database URL into a generated application. Development, test, and
production connections must be distinct selections; automated tests must not
fall back to a production target.

Persist project secret records in both supported Zelyq database dialects if new
tables are required. Apply team/project authorization to every write and use.
Audit changes without values. Only authorized project editors may configure
backend secrets, subject to existing team policy.

The server resolves authorized secret references and supplies values directly
to the target runtime service. Agent prompts and tool results receive names and
availability, not values. Remote delivery uses the authenticated runtime channel
with an appropriately protected transport. Supply child processes with an
explicit environment allowlist; the local driver's existing `process.env`
inheritance must not leak Zelyq credentials into the new service path.

Never emit secrets into `VITE_*`, source files, generated clients, logs, snapshots,
Git, exports, or preview metadata. Redaction is defense in depth; generated code
must also avoid logging credentials. Missing required configuration produces an
actionable state rather than a fabricated credential or a misleading success.

### Data and undo

Keep Python environments and caches out of source snapshots: `.venv`,
`__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, and generated coverage
artifacts. Apply corresponding rules to template collection, file search, eval
preparation, Git ignores, and export paths where relevant. Exclusions must not
hide authored Python files or tests.

Store persistent uploads and application data outside the source snapshot tree.
Code undo restores source and lockfiles, then re-synchronizes environments and
restarts services as required. It does not undo database migrations or external
side effects. Test code/schema incompatibility and report it honestly. Deleting
or disconnecting a Zelyq project removes its connection references and secrets;
it must not silently delete the user's external databases, tables, or hosted data.

## 7. Agent behavior and verification

Resolve frontend, backend, runtime, and persistence capabilities once and pass
the same validated context through project service, gateway, agent session, and
specialist dispatch. An imported project with an unsupported layout must get an
accurate limitation rather than invented stack metadata.

Update all instruction paths together:

- Architect Mode: choose Python when the requirement warrants it; design API
  contracts, authentication, persistence, process boundaries, and deployment.
  Establish the user's database engine, existing schema, identity provider, and
  schema ownership before proposing persistence changes. Do not mandate Supabase.
- Builder: implement FastAPI routes and React integration within that design.
  Use the selected SQL or Supabase path. Preserve the current browser-to-Supabase
  workflow only for projects explicitly using that mode.
- Stack guide: teach Python layout, uv usage, error handling, typing, bounded
  requests, and supported persistence conventions.
- AI integration: allow server-side Python provider calls for Python projects,
  while preserving project/user credential ownership and the existing Edge
  Function workflow elsewhere. Do not duplicate the same feature across both.
- DevOps and QA specialists: support Python config/test paths and commands with
  narrowly adjusted write scopes. Do not remove their existing boundaries.
- Shell tooling: recognize Python server/watch commands as managed lifecycle
  work, including Uvicorn, instead of letting them block a turn indefinitely.

Replace the root-package-only verification assumption with a declared check
plan. The first starter must run frontend typecheck/build, Python lint/type
checks, pytest API tests, and API-client consistency checks. Check service
readiness when a preview is running. Expensive end-to-end suites may run at
completion/release gates, but an API failure must never be masked by frontend
success.

Report checks individually as passed, failed, or not run, with the reason.
Missing dependencies, unavailable credentials, or a skipped API test are not
passing evidence. Backend failures must reach the existing repair loop.

Add eval cases for a bounded CSV report, a custom calculation, protected data
access, an existing PostgreSQL schema, a read-only MySQL reporting database, an
intentional backend regression, and a task that does not need Python. Include a
case with an existing identity provider and no Supabase connection.
Measure successful completion, repair behavior, installation/startup time,
resource use, and agent cost. Record actual results before claiming improvement.

## Implementation state

What exists, and what a reader should not assume from its existence.

### Built and verified

**A new project saves data with no configuration, on a machine with no Python
toolchain.** Verified through the HTTP server the way a person uses it:
register, create a React + Python project, start the preview, POST a row, read
it back, and find it still there after a preview restart — with the database
file outside the source tree. Separately verified with `uv` absent from PATH
entirely: Zelyq fetches and verifies it, and the same flow works. Setting up a
language toolchain is the platform's job; the user is asked only when it is
genuinely impossible, and then the message says why.


| Area | Where | Evidence |
| --- | --- | --- |
| Runtime manifest contract | [`packages/core/src/project-runtime.ts`](../packages/core/src/project-runtime.ts) | Schema-validated and version-pinned; escaping working directories, unknown keys, unknown versions, and reversed service order are refused. `packages/core/test/project-runtime.test.ts`. |
| Service supervision | [`packages/runtime/src/managed.ts`](../packages/runtime/src/managed.ts) | Supervisor starts the API, waits for readiness, then starts the frontend with its proxy target. Crashed services fail the aggregate preview and drop its URL; it survives the Zelyq process that started it, so a preview can still be adopted. Per-service status is schema-parsed and size-capped on the way back, because a project file writes it. Log output is bounded, and configured secret *values* are redacted by substring — which is defence in depth, not a guarantee against code that deliberately re-encodes them. `packages/runtime/test/managed.test.ts`. |
| Dependency synchronisation | `installManagedDependencies` | Fingerprinted over both lockfiles; a changed lock or a deleted environment re-synchronises, an unchanged one does not reinstall. |
| Operation serialisation | `withManagedLock` | A filesystem lease per project, so the server and agent drivers cannot start two service groups. Released on failure; stale leases expire. |
| Toolchain provisioning | [`managed.ts`](../packages/runtime/src/managed.ts) | Zelyq installs `uv` itself when the host has none: the pinned release is downloaded from GitHub and checked against its published SHA-256 — never an install script piped to a shell — unpacked into `<workspace>/.zelyq-toolchain`, and put first on the PATH project commands use. The user's shell profile is untouched, no sudo is involved, and nothing is written outside the workspace. One provisioning per workspace, leased so concurrent starts cannot race. Verified on a machine with no `uv` on PATH: capability reported in ~2s, project commands then see it, preview runs and saves a row. |
| Capability negotiation | `local.ts`, `container.ts`, `remote.ts`, `apps/runtime-host` | The local probe provisions the toolchain and reports what it actually achieved, using the exact shell and environment project commands run in; the reference host forwards what its own driver reports rather than a constant; remote requires the host to advertise `react-fastapi-v1`. When provisioning genuinely cannot work — Windows, an unsupported architecture, no network, an operator-chosen container image without `uv` — the error names the cause and the one command that fixes it. Verified on the local driver, and on the container driver with Zelyq's own sandbox image on a live instance. The container probe builds that image before asking it anything — on a fresh install it used to ask a registry for a tag that only exists locally — and on the container runtime a "no" is asked again after a minute rather than kept until a restart. On the local runtime a failed `uv` download is still remembered until the server restarts. |
| Stack availability | [`templates.ts`](../apps/server/src/services/templates.ts), [`projects.ts`](../apps/server/src/services/projects.ts) | `requiresCapability` hides the stack from project creation on a runtime that cannot run it, and creation refuses it directly rather than scaffolding a project that can never preview. |
| Starter template | [`templates/react-fastapi`](../templates/react-fastapi) | All six declared checks pass from the committed locks: frontend types, frontend build, Ruff, mypy `--strict`, pytest (21 API behaviour tests, including the production start's migration), and the OpenAPI/TypeScript contract check. The contract check generates into a scratch directory and compares, so a repeated run cannot absorb its own failure into the working tree. |
| Preview lifecycle | Local driver, end to end | A scaffolded project installs both toolchains and serves a browser-to-Python request through the Vite proxy; stop releases both processes and reports every service stopped. |
| Local-first persistence | [`project-runtime.ts`](../packages/core/src/project-runtime.ts), [`project-backend.ts`](../apps/server/src/services/project-backend.ts), [`managed.ts`](../packages/runtime/src/managed.ts) | An unconfigured project resolves to its own writable SQLite database; `readOnly` follows ownership rather than defaulting to read-only; the supervisor applies migrations for that database only, gated server-side. CI applies the starter's migration to an empty database and fails if the models and migrations have drifted apart. `apps/server/test/project-backend.test.ts`. |
| Configuration and secrets | [`project-backend.ts`](../apps/server/src/services/project-backend.ts) | Values are write-only and encrypted at rest; platform-owned variable names are refused; engine/URL mismatches, non-HTTPS identity endpoints, and the cloud metadata address are rejected. The server places secrets in the backend service environment only — never in `env`, the browser bundle, preview metadata, or agent context — and the container path passes values through the engine's environment rather than its argv. Note the limits of this. The agent authors the Python that *receives* those secrets, so a backend route can always disclose what it is given. And the agent's own commands run as the same user as the API process (in the same container, on the container runtime), so a command it chooses to run can read that process's environment. The boundary is on delivery — secrets are never put in the agent's context, prompts or logs — not on what code or commands in the project can reach. `apps/server/test/project-backend.test.ts`. |
| Production container | [`templates/react-fastapi/Dockerfile`](../templates/react-fastapi/Dockerfile) | Builds and serves the UI and API from one image as a non-root user. On start it brings the app's own SQLite database up to date before the API accepts requests (`app/prestart.py`) and never migrates a database somebody else owns; a saved row survives a restart on the same volume. Also: SPA refresh returns the app, an unknown `/api/*` route returns a JSON 404 rather than `index.html`, path traversal is refused, and a protected route with no identity provider configured fails closed. |
| Continuous integration | [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) | A `python-starter` job installs from the committed locks and runs every starter check; the docker job builds the starter's production image. Python advisories are reported without failing the build pending an exception policy. |

### Known limits of what is built

- **Backend configuration has three environments; only `development` is read.**
  Previews, checks and connection tests all use it. `test` and `production` are
  stored and encrypted but nothing consumes them yet — the editor says so rather
  than implying otherwise.
- **Loopback and link-local database hosts are refused** (including inet_aton
  shorthand, integer/octal/hex spellings, IPv4-mapped and IPv4-compatible IPv6,
  and a trailing-dot `localhost.`), because a connection test runs on the Zelyq
  host's network. A name is looked up when it is saved, so a public name that
  points at loopback (`localtest.me`) is refused too — but a name can resolve
  differently later, and a name the Zelyq host cannot resolve is let through.
  A host given in the URL's query string (`?host=`, `?hostaddr=`) is not
  checked yet, and the driver connects to it.
  The runtime's network policy is the real boundary. RFC1918 addresses stay
  allowed: restricting a private network is operator policy, not a string check.
- **Read-only access is enforced per transaction** on PostgreSQL, MySQL and
  SQLite, and is defence in depth — read-only database credentials remain the
  real boundary.
- **A private-CA database needs `DATABASE_SSL_ROOT_CERT`.** TLS verification is
  always on; supplying a CA is how a self-signed or internal CA is trusted.

### Not yet built

These remain open. Nothing above should be read as covering them.

- **Real engine integration.** PostgreSQL and MySQL connection, transaction,
  rollback, and permission behaviour have not been exercised against live
  engines. Only the configuration and connection-assembly paths are tested.
- **Migrations against a user's own engine.** The starter's migration is
  generated, applied and drift-checked against SQLite in CI, and applied
  automatically for the local build database. No migration has been exercised
  against PostgreSQL or MySQL, and authorized baseline adoption on an existing
  schema is unimplemented.
- **Existing-schema discovery.** `describe_database` reads metadata for selected
  tables only and never samples rows, but it has not been run against a populated
  external database.
- **Authorization testing.** Two-user cross-access checks against the real API,
  and expired/rotated-token behaviour against a controlled identity-provider
  fixture, are not written.
- **Runtime conformance.** [`conformance.test.ts`](../apps/runtime-host/test/conformance.test.ts)
  has no Python fixture, so the remote host's managed-service lifecycle is
  unverified. The remote runtime has not been exercised with this stack. The
  local and container drivers have, the container one on a live instance
  rather than in CI.
- **Agent evaluation.** None of the eval cases in section 7 exist, and
  [`workspace.ts`](../apps/agent/evals/workspace.ts) does not prepare a Python
  project.
- **Measurement.** No startup time, image size, memory, or agent-cost figure has
  been recorded. The one observed cold start — both toolchains installing from
  warm caches on one Linux host — is not a benchmark.

## 10. Risks and decisions to settle before implementation

| Risk or open detail | Required resolution |
| --- | --- |
| Platform complexity from another language | Keep Python inside generated project services; retain TypeScript platform contracts. |
| Host compatibility and native wheels | Record exact supported Python/OS/architecture combinations and verify them in phase 1. Initial support must not imply all Python packages work. |
| Cold installs and larger images | Measure first-start time, image size, and memory; use bounded caches without sharing writable project environments. |
| Preview exposure | The current deployment proxy routes directly to preview ports. Editor authorization alone does not make that URL private. Specify preview access policy before using sensitive sample data; retain application API authentication independently. |
| CPU-heavy requests | Bound initial workload size/time. Move durable or heavy work to a separately designed worker capability later; `async` alone does not make computation non-blocking. |
| Manifest and protocol evolution | Version the schema, define old-client aggregate behavior, and test capability negotiation. |
| Backend credentials in generated code | Establish project ownership, secret injection, and allowed environment policy before enabling credential-dependent features. |
| Migrations and code undo | Separate code recovery from database lifecycle; document the supported response to incompatible schema changes. |
| Existing user data | Keep discovery read-only and schema-scoped; make ownership explicit and test that onboarding never issues DDL or reads sample rows without authorization. |
| Engine differences | Pin/test PostgreSQL, MySQL, and SQLite separately; do not infer behavior from SQLAlchemy support or a SQLite-only test suite. |
| Private database connectivity | Probe from the runtime and document operator-controlled network access and TLS; never work around isolation silently. |
| Identity and database coupling | Verify independent auth plus user-managed persistence end to end; Supabase remains optional. |
| Scope growth | Complete one deployed, verified React/FastAPI workflow before adding frameworks, native-mobile routing, or queue infrastructure. |
