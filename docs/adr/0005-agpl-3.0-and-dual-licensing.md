# 5. Relicense to the GNU AGPL-3.0 with a commercial dual-licence

- **Status:** Accepted
- **Date:** 2026-08-30
- **Supersedes:** [ADR 0004](./0004-sustainable-use-license.md)

## Context

[ADR 0004](./0004-sustainable-use-license.md) moved Zelyq from Apache-2.0 to the
Sustainable Use License — a *source-available* licence — to stop a well-resourced
third party from reselling Zelyq as a hosted service. That worked for the
resale problem but cost two things:

- Zelyq could no longer honestly call itself "open source." That is a real
  positioning and community cost — see the "not real open source" criticism the
  ADR 0004 anticipated.
- Some organisations' procurement and legal policies pass OSI-approved licences
  and block everything else outright, with no exception process.

The goal has not changed: fund full-time development, and don't hand the one
activity a hyperscaler does best — running a closed hosted service — to a
hyperscaler for free. The question is whether that is achievable with a
*genuinely* open-source licence. It is: the GNU Affero GPL is OSI-approved, puts
no restriction on *running* the software, and its §13 "network use" clause is
itself the protection — anyone who runs a **modified** version as a network
service must offer users the source of their modifications.

The project is still small, has one copyright holder (Dee Empire), a CLA from the
start, and no release has yet carried the Sustainable Use License. The cost of
changing again is near-zero now and only rises.

## Decision

Relicense everything except `research/` (stays CC BY 4.0) and "Zelyq Enterprise"
components (stay under `LICENSE_EE.md`) from the Sustainable Use License to the
**GNU Affero General Public License, version 3**.

Alongside it, Dee Empire offers a **commercial licence** for the same code under
terms that do not carry the AGPL's network-source requirement, for:

- embedding Zelyq in a closed-source product;
- running a modified Zelyq as a service without publishing the modifications;
- organisations whose policy blocks AGPL software.

Keep the structure ADR 0004 established:

- **Open core.** `ee` / `.ee` paths remain under the Zelyq Enterprise License
  (`LICENSE_EE.md`), a paid subscription. Nothing that has ever been in the AGPL
  core moves there.
- **CLA retained.** Dual-licensing requires it: a contribution received only
  under the AGPL cannot be re-offered under a commercial licence. `git commit -s`
  plus first-PR confirmation.
- `v0.1.0` and every earlier commit remain available under Apache-2.0;
  irrevocable.

## Consequences

**Good**

- Zelyq is genuinely open source (OSI-approved). The "source-available / rug
  pull" criticism does not apply, and OSI-gated procurement passes for the core.
- The resale protection is intact and arguably stronger: the AGPL travels with
  the code, so a *closed* modified fork run as a service is a licence violation,
  not merely something a permissive licence failed to prohibit.
- Three revenue lines instead of one: the commercial licence, the Enterprise
  subscription, and a hosted offering.
- The enterprise boundary is still defined before anything sits behind it.

**Costs**

- Some organisations blanket-ban the AGPL even for pure self-hosting (a few large
  ones do so as policy). Those become a commercial-licence conversation or a lost
  user — the same trade ADR 0004 accepted, with a different trigger.
- Downstream users who modify Zelyq *and* run it as a network service take on the
  AGPL §13 obligation to publish their changes. Plain self-hosting, modified or
  not, does not.
- Dependencies must stay GPL-compatible. Apache-2.0, MIT, BSD, and ISC are
  one-way compatible into (A)GPL and remain the allowed set in `CONTRIBUTING.md`;
  a GPL-incompatible dependency is now a hard blocker, not just a preference.
- A second relicence in three days reads as churn. Mitigated by doing it before
  any release carried the interim licence, and recording why here.
